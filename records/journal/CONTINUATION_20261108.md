## User Goal & Observed Initial State

- Goal: reach an interactive iOS graphical UI on the physical device; the user explicitly requested removing the custom-drawn fake Apple logo.
- At session start, Windows enumerated `USB\VID_1209&PID_0001\PROBE`, while neither `adb` nor `fastboot` listed any device. Probe status query (`0x46`, value `0`) reported `launch=1`, `stage=8`, `active=1`. That status alone does not prove XNU, userland processes, or the UI are currently healthy.
- Earlier `userland-drive-logs/live_stream.log` recorded `SpringBoard` and `backboardd` reaching `running` in `launchd`, alongside repeated `mediaserverd` exits (`OS_REASON_EXEC` / code `0x8`). A process marked `running` by `launchd` does not prove a usable desktop. The earlier `real_display_preview.png` showed kernel console text, not iOS UI.
- Source inspection confirmed `ios-fuxi/shim/fuxi-loader/loader.c` no longer contained `draw_apple_logo`, `apple_boot_asset`, or `apple_logo`, while still clearing the framebuffer. Source inspection alone does not prove every binary payload or runtime path lacks graphics assets.
- Root `fuxi-xnu-boot.img` and `out/fuxi-loader-logo/fuxi-xnu-boot.img` both had SHA-256 `7729d67d2de4de6052e016aac442c020a83c17a5b316a6e856902ba15bce73a7`; `.bak` was `feed8b123698ad22af85bac6c4521076cb8948581ea9763488206fd11fc4f738`. File hashes on disk do not prove which image is currently running in RAM.

## Verifiable Gaps in the Display Pipeline

- `ios-fuxi/xnu27/series` and `0004-components.patch` did not wire the older `SweetFramebuffer.cpp` into `xnu-12377`; the K5 roadmap plans to port display, backlight, touch, and buttons. Confirming whether another display implementation is prelinked requires inspecting the actual kernel binary and live `IORegistry`, not just source patches.
- The older `ios-fuxi/xnu/fuxi-unixnu/SweetFramebuffer.cpp` comments describe a CPU renderer depending on `SweetSurface.h`, copy/display helpers, and multiple FUXI surface/backlight/Adreno/perf interfaces gated by `SWEET`. `xnu27` defines `FUXI` machine flags, so copying a single file does not yield a working port. Earlier claims that "iOS strictly requires Metal and has no CPU path" lacked evidence and were discarded.
- Actionable path: inspect the booted kernel symbols and live `IORegistry` for `AppleCLCD` / `IOSurface` providers; build a dependency/ABI inventory from `xnu-8796` to `xnu-12377`; port a minimal display service in isolated build outputs and verify registration, user-client open, swap, visible panel output, and finally touch—never substituting mock frames or process survival for visual verification.
- This Windows host had no `xcrun`; NDK can build the bare-metal loader, not `xnu-12377`. `xnu27/README.md` specifies a macOS / Xcode 26-class build environment, and no remote macOS builder was verified, so no new `xnu-12377` kernel was built or loaded here.

## 2026-11-08 Continuation: Evaluating the Native iOS 16 Kernel Path First

- `ios-fuxi/README.md` documented that `xnu-8796` already included CPU display, touch, and desktop paths (as an upstream claim, not yet verified on this handset). Porting display directly into `xnu-12377` was therefore not the only option.
- Downloaded `xnu-8796` `fuxi-kernel-metal4` from public fork `zgl97/ios-fuxi` Actions run `42244366810` (run and kernel job succeeded; `build.log` recorded commit `979e2f08c704677bb75934ae96d4686ba9d1692b`; all 40 manifest SHA-256 hashes matched). Saved locally under `candidates/kernel-metal4-zgl-42244366810/`. Note: this is a third-party CI artifact, not a local rebuild or device verification.
- Built an isolated RAM-only diagnostic image `candidates/kernel-metal4-zgl-42244366810/diag-loader/fuxi-diag-ram.img` (SHA-256 `f28831b2d493fdc17771278810334ffbf601903f5e1ced3e381752db11d12937`) using that kernel, public ADT, and `sweet-init.S`. Boot-args: `-v debug=0xc serial=3 cpus=1 keepsyms=1 rd=md0 sweetlog=0 wdt=-1` (no UFS probe/read/write args; static init in RAM is not an iOS desktop). Structural and firmware hash checks passed in `scripts/build_diag_loader.py` without overwriting existing boot images.
- Old `extents.json` matched `fuxi-root.adt` and recorded 701 non-coalesceable extents for `/data/ios16-root.img`, whereas the old kernel source limit was 512 and that 26,192-byte ADT exceeded the 16 KiB v1 payload limit. `scratch/stage_root_and_boot.py` contained a command deleting `/data/ios16-root.img` (unconfirmed whether executed). Non-overlapping extent lists do not guarantee old allocations remain valid—never write to stale extents.
- Read-only probe sample over 12s showed XNU log count advancing from `779,319` to `789,393` with `mediaserverd` still restarting on `OS_REASON_EXEC` (saved in `diagnostics/live-20261108-165440/kernel-ring-tail.bin`). Built `candidates/vm-tools/ios16-root-build.img` (20 GiB, SHA-256 `5fc67460bcbdc1de0a6a076daa8cfb01c47ecfc71c2a5760cb8ab5a7acaa2864`) inside an isolated Alpine QEMU VM from three read-only inputs. No `mobileactivationd` container was found in source images and no data ark was pre-staged, so post-boot activation state remained to be verified.
- Extracted the D22AP device tree from Apple 20H392 firmware and added 61 `/product` properties to the production candidate ADT. Created `/data/ios16-codex-b.img` on device (inode `152183`, 160 extents, 20 GiB, `lsattr` `C`); initial `FIEMAP` matched the ADT and did not overlap `ios27` or the unused 20 GiB `/data/ios16-codex.img` candidate (664 extents).
- Fixed an upstream bug in `scratch/f2fs_io.rs` that misreported GC count `0` from `F2FS_IOC_GET_PIN_FILE` as `unpinned`. Also cleared up an earlier misread of `FIEMAP` flag `0x1000` as `UNWRITTEN`: NDK headers define `0x1000` as `MERGED` and `0x800` as `UNWRITTEN`. - Unmounted `/data` and `/sdcard` before writing; the dedicated writer refuses mounted `userdata` and restricts writes to the verified 160 extents, device `major`/`minor`, and exact capacity. Because Windows `adb` `stdin` treats `0x1a` as `EOF`, early tests wrote partial data; switching to local ADB TCP forwarding yielded an exact first-1-MiB readback match. Full streaming and byte-readback tooling are in `scripts/stream_ios16_candidate.py`, `scripts/verify_ios16_candidate.py`, and `diagnostics/ios16-candidate-write-v4.log`.

## Backup & Write Boundaries

- Verified all 21 partition images against `backup/checksums.sha256` (`21/21` matched). This verifies local file integrity against the existing manifest only; it does not compare against live device partitions, prove user-data coverage, or test restoration.
