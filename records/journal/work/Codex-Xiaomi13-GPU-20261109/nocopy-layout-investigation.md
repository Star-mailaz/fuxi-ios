# Fuxi compressed texture investigation

## Device evidence

The diagnostic desktop boot recorded a refused `newTextureWithBytesNoCopy:length:descriptor:deallocator:` request: 1125 × 2436, Metal format 204 (`ASTC_4x4_LDR`), one mip level, shader-read usage, a page-aligned 2,752,512-byte allocation, and no deallocator. The backboardd survey recorded 16 stored GPU frames and then a CPU fallback. See `native-nocopydiag-touch-survey-boot-1/boot.log`.

The 2,747,808 bytes required for tightly packed ASTC 4 × 4 blocks round up to 2,752,512 at 16 KiB. That size alone does not establish how the allocation's blocks are ordered or whether another layout is used.

## Static findings from the same local iOS root

The read-only cache inspection decoded selector references and Objective-C stubs in QuartzCore. Addresses below are unslid and specific to this local cache; the symbols are stripped, so the relationship to the observed dynamic request is not yet established by a stack trace.

- The call at `0x188483ffc` invokes the no-copy selector. It passes a source-object pointer at offset `0x58`, an aligned size, a descriptor, and a nil deallocator.
- The byte at source-object offset `0xa8` selects the no-copy path when bit 0 is clear. When bit 0 is set, the code creates a normal texture and calls `replaceRegion:mipmapLevel:slice:withBytes:bytesPerRow:bytesPerImage:` for each mip using object-provided level offsets and row strides. It does not retry that alternate path when the no-copy call returns nil.
- The producer code around `0x188358b00` uses an existing layout object's `alignment`, `initializeTextureMemory:`, `copyFromLinearBytes:...toTextureMemory:...`, and `finalizeTextureMemory:`. It constructs the compressed-source object at `0x18837cd78`, then sets bit 0 at `0x188358d0c` according to whether transformed memory exists. The successful transform branch clears bit 0 and therefore points toward the no-copy consumer path.
- Another decode path around `0x18849db74` requests a texture-layout object and uses its size and alignment when allocating a destination. It copies a pre-existing byte span into that allocation, calls the same compressed-source constructor at `0x18849dc84`, and sets bit 0 from serialized metadata at `0x18849dcec`. Static inspection alone does not establish what generated that data or which path handled the observed device request.
- QuartzCore has two direct static callers of the same layout helper at `0x188358aec` and `0x18849db74`: the conversion producer and the decode path described above. ImageIO separately sends `watermark` to a layout object at `0x18bb032b8`; a caller at `0x18bafe6e0` obtains the resulting two words and compares them with two words in its input metadata. A differing value follows a separate branch. This is evidence that this particular ImageIO path distinguishes layout identifiers; it does not establish how every cached allocation is validated or what this boot's allocation contains.

Evidence files: `nocopy-quartz-functions.log`, `nocopy-quartz-function-disassembly.txt`, `nocopy-quartz-candidates.log`, `nocopy-candidate_flags-disassembly.txt`, `nocopy-candidate_init-disassembly.txt`, `nocopy-candidate_decode-disassembly.txt`, `nocopy-quartz-layout-xrefs.log`, `nocopy-imageio-layout.log`, and `nocopy-watermark-xrefs.log`.

## Interpreting a future caller trace

Read-only inspection of `native-uchar3-root.img` found shared-cache UUID `8f970452-c9e3-3e88-b114-feb1864bc9e0`; the QuartzCore image has UUID `9e40b2eb-260c-3af1-ae45-a1a551a8c1b9`, recorded text base `0x188284000`, and size `0x34d000` (`nocopy-cache-identity.log`). This identifies that inspected cache, not automatically a later boot's cache. Independently read and verify the cache identity for the actual candidate before applying these addresses.

The host `native-nocopydiag-root.img` source and `native-uchar3-root.img` were mounted read-only in a local guest, and all 44 `dyld_shared_cache_arm64*` files, including symbols, had identical names, lengths and independently computed SHA-256 digests (`nocopy-cache-compare.log`). The main cache SHA-256 is `76874e8375252ee643011ff8063f0cce12355f05cf5f9897a34e5679667a65aa`. This ties the static analysis to the pre-boot diagnostic source image, not to the phone's current post-boot contents or a future candidate; verify the actual candidate separately.

Subsequently the officially mapped phone candidate was completely backed up and independently hash-verified as `native-phone-precaller-current-backup.img`, SHA-256 `831a1828e3cf6b4b388f70291368f73d627267d45df6119a7ab74dc648232c2b`. A read-only comparison of this backup against `native-uchar3-root.img` found all 44 cache files identical by SHA-256 (`native-precaller-current-cache-compare.log`). This validates the cache identity at the time of that backup; any later modified candidate still needs its own verification.

`resolve-nocopy-frames.py` interprets the caller diagnostic's image-relative frame metadata only after the operator supplies the matching cache UUID. It recognizes the exact return address after the static QuartzCore no-copy call, reports unmatched frames without guessing, and rejects a UUID mismatch. Synthetic tests covered that exact match, a neighboring address, a different image path, an unknown frame, an out-of-range offset, a UUID mismatch and a malformed log. An exact match identifies that consumer call site, not which producer generated its memory, its layout, mutability or lifetime.

The bounded on-device survey later captured a real stack in `native-caller-survey-boot-1/boot.log`. Frame 1 was QuartzCore + `0x200000`, the return after the call at `0x188483ffc`; it matches the consumer described above. The recorded device request was ASTC 4 × 4 LDR, 1125 × 2436, length 2,752,512, no deallocator, and shader-read usage. The survey reached 22 stored GPU frames before refusal and CPU fallback. The actual frame confirms the consumer, but does not identify either static producer or establish the texture-memory layout. The separate device smoke passed ASTC compressed roundtrip, four colors, partial update and 131,072 sampled pixels; those used an explicitly uploaded linear fixture, so they cannot establish the unknown raw allocation's layout. The phone returned to Android after the bounded survey.

Further offline disassembly of the actual higher frames (`nocopy-stack-windows-disassembly.txt`) shows frame 2 is the return after a direct call to the consumer function at `0x188483cb0`; the caller passes its `x25` object as the consumer's third argument, consistent with the consumer reading that object's `+0xa8` flag and `+0x58` pointer. Frame 3 is an indirect virtual call and does not identify the object producer. The shared compressed-source constructor at `0x18837cd78` initially sets both low bits of `+0xa8`; the direct constructor path at `0x188358a40` clears bit 1 only and then branches past the other path's bit-0 update. Therefore, if that constructor and branch execute as disassembled without a later mutation, that direct path retains bit 0 set and selects the ordinary upload branch, not this observed no-copy branch. Another constructor call at `0x18837a660` explicitly overwrites bit 0 using a prior boolean; the existing decode path also sets bit 0 from metadata. These are static inferences; they do not establish which path created the runtime object or prove its layout.

## Consequences for a repair

The request must not be implemented by assuming a tight linear layout merely from the format and length. One plausible direction is to support a matched pair: a layout object that advertises and produces a defined block layout, and a no-copy consumer that interprets exactly that layout while preserving lifetime and synchronization. Existing DroidVM code documents such a device-specific layout and watermark, but its assumptions have not been validated for this Fuxi/iOS path. A cached or externally generated allocation may carry another layout.

Before deploying a repair, establish the dynamic caller and where the relevant bytes were generated; test layout negotiation, cache/watermark invalidation, compressed texture pixel output, lifetime and synchronization, unexpected layouts, and desktop fallback. Then verify sustained GPU composition and physical display and touch behavior. A successful build or a few stored GPU frames is insufficient.
